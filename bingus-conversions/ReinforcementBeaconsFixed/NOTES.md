# Reinforcement Beacons Fixed data-v4.6.1 -> Steam build 26088801 (plain LuaJIT)

Megapack option `ReinforcementBeaconsFixed`, module `mods/cowboybingus/reinforcement_beacon_fix_data` (resource
`4f1ba22daa1eab5c`). Source: `upstream-bingus/ReinforcementBeaconsFixed` at tag v4.6.1; every file the lock pins
(`components.lock.json` source_sha256) matches it and the pack's pinned copy. Only build data changed; the code is the
upstream LuaJIT code (real `ffi`/`bit`/`jit`), no PORT51/compat51/cffi.

Why the installed copy says `reinforcement_beacon_fix_data:1520: Unsupported game module`: archive_loader.lua
compares game.dll's SHA-256 with the old build's pin before doing anything. The port carries the new pins.

## Writes (the module's only memory writes)
1. `write_correction` / `write_xy` (spawn_data.lua 457): 8 bytes (two floats, target XY) at `[game.dll+0x2CE1618] +
   0x10C`, only when the local player owns the spawn, `[pm+0x2E0] == 2` (pod pending), countdown 0.1..5.1 s, the
   beacon association was re-read immediately before, target within 512 m; `api.write` checks private read-write
   memory first. Evidence: PLAYER_MANAGER global (47 witnesses), +0x10C is where the game's own AC83F0/AE4610 stores
   the beacon position for the pending spawn (identical code), +0x2E0 state values unchanged.
2. Rollback in `write_correction` (462): the original 8 bytes, same address, only while `[pm+0x2E0] == 2`.
3. `patch.restore` (579): the original 8 bytes, only if the same manager, state 2 and the address still holds this
   mod's bytes.
No code or executable memory is written.

## Read-only in-game checks: `live/reinforcement_readonly.lua` (eval it through the memory tool)
- L1 `[game+0x2CE1850]`: ship -> +8 = 0 or +0x40 = 0; mission -> +0x40 in 1..7.
- L2 `[game+0x2CE1618]` (null on the ship is fine): +0x84 = players (1..4), +0x88 <= 4, +0x2E0 = 3 while alive, 1
  dead and queued, 2 pod pending; +0x3B4 < 32; +0x10C XYZ = the pod's landing point while state 2 and +0x12C counts
  down from ~5 s to 0.
- L3 `[pm+0xE8]`: +8 your entity id, +0x14 bit 0 = 1 (host or your own player).
- L4 `[game+0x2CE1B78]`: +12 active <= +8 capacity <= 128; per beacon the id, owned bit, use bits, and through the
  position lookup `hashmap([game+0x2CE1CE0]+0x28, id)` a position at the beacon you see (place one, then read).
- L5 `[game+0x2CE1860]`: solo, right after a death a row of type 0x7F with your death/anchor XYZ; never expect 0x7C.
- L6 `[game+0x2CE41B8]`: lookup +0xF24990 capacity a power of two; `hashmap(EM+0xF24990, unit_ref)` -> index; record
  `EM+0xF349E0+24*index` +8 equals the L3 id (MATCH), +12 engine ref.
- L7 `[exe+0x1AB76F8]`: slot < +0x98, generation byte matches, `[[obj]+0xE8] - exe == 0x28D3A0` (OK), world position
  near your character.
- L8 `[game+0x2E287D0]+0x3C`: a plausible world position.
- L9 region of pm+0x10C: protect 0x4, state 0x1000, type 0x20000.
In game, the mod's log then shows `waiting_for_reinforcement` (alive), and after a beacon-assisted reinforcement
`beacon_spawn_centered` / solo `solo_spawn_centered` with `corrections=1` and the from/to XY.
